    // Framework_Structure

    How the suite
    is organised

    The layout of the public sample repo: tests, data, client and CI each have one job. No client code or names.

    Repo // api-automation-samples7 files
    api-automation-samples/
    ├─ .github/workflows/
    ├─ BookingApi.Tests/
    │ ├─ Builders/
    │ └─ BookingApi.Tests.csproj.NET 10 · NUnit 4 · RestSharp · Bogus
    ├─ .gitignore
    └─ README.mdcoverage table · how to run
    L1 // TestsBookingTests.cs

    Test layer

    Arrange / Act / Assert, grouped with Assert.Multiple. Tagged [Category] so CI can run Smoke and Regression separately.

    builds payload
    L2 // Test dataBookingBuilder.cs

    Data builders

    Fluent builder with Bogus: every run gets fresh, realistic data, and tests override only the fields they care about.

    sends request
    L3 // ClientApiTestBase.cs

    Shared API client

    One RestClient, a cached auth token, config via RunSettings, and a pinned Accept header.

    ↺ [TearDown] deletes every booking a test created, so runs stay independent.
    HTTP · JSON
    SUTrestful-booker.herokuapp.com

    Restful-Booker API

    Public practice API, so tests create their own data instead of relying on seeded records.
